# M6 孤儿判定准确性

## 目标

降低孤儿进程误报：区分「意外遗留」与「有意守护」，让用户对明知是有意开启的后台进程有一键豁免手段。核心诉求来自使用反馈："很多疑似孤儿都是我开启的后台进程"。

## 问题诊断

当前判定是纯结构判断（父 PID 不在进程表 → Confirmed），三个缺口：

1. **无父进程身份记忆**：父死后不知道父是谁。`explorer.exe` / `svchost.exe`（DCOM 启动器）拉起的正常应用，父进程退出是 Windows 常态，与 IDE 终端遗留的 node.exe 被判成同一类
2. **无豁免机制**：用户明知有意开启的进程仍被反复标红
3. **来源一刀切**：真正该抓的是终端/编辑器遗留（父为 cmd / WindowsTerminal / code 等）

## 范围

- 后端：父进程身份记忆（快照间记录 pid → 父进程名，PID 复用防护）
- 后端：已知系统启动器来源降级为新状态 `expected`（正常守护，不计入孤儿）
- 设置：孤儿豁免名单（exe 名精确匹配，小写），命中不再判定为孤儿
- 前端：详情侧栏展示父进程身份 + 豁免/取消豁免按钮；设置页管理豁免名单
- 状态文案：`none` / `expected` / `confirmed` 三级

## 非目标

- 命令行模糊匹配 / 路径规则豁免（先做 exe 名精确匹配）
- Windows 服务（SCM 注册）识别
- 首轮启动时历史为空的"父身份未知"进程自动降级（保持 Confirmed，随运行时间改善）

## 验收标准

1. 由 explorer 启动的应用（父为已退出的 DCOM 启动器）标记为 `expected`（正常守护），不出现在孤儿过滤视图与孤儿计数中
2. 终端遗留的 runtime 进程（父为已退出的 shell/IDE）仍判 `confirmed`，且详情显示"父进程 xxx 已退出"
3. 详情侧栏点「标记为有意后台进程」后，该 exe 名进入豁免名单，所有同名进程不再判孤儿；设置页可查看/移除
4. PID 复用场景：父 PID 被新进程复用仍判 `confirmed` + pidReused（回归不破）
5. `cargo test` / `cargo clippy -D warnings` / `npm run build` 全绿
